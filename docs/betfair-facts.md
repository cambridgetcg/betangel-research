# Betfair facts: what the code relies on, and how sure we are

Prepared **2026-10-10**. Fact register for `betangel_research/betfair`, not evidence of profitability. 14 rows were re-read on 2026-10-12; on 2026-10-13 Yu ran read-only delayed-key first-live tests (T1, T4, T6, T7 and part of T8). No order has been placed, and most facts are still unchecked against the live Betfair API.

**每個外部事實都要有出處、等級同處理方法；未驗證就照寫未驗證，代碼要預最壞情況。**

呢份係 [`research/betfair-facts.json`](../research/betfair-facts.json) 嘅人讀版本。[接入指南](betfair-integration.md) 同 [落單路徑](betfair-order-path.md) 入面嘅 F-id 全部指返呢度。`constants.PROVENANCE` 將每個 public constant 對應到呢度嘅 F-id。冇任何程式自動生成呢份文件：改事實要先改 JSON，再改返呢度嗰一行；`tests/test_betfair_facts_doc.py` 會逐格對比兩邊，唔夾就 fail。

## How to read a row

- **value used**：代碼用嘅講法，paraphrase 唔係原文引用，規則係最多一句（spec §15）。呢度同 JSON 入面嘅 "spec section N"／"spec §N" 指嘅係 binding spec [`final.txt`](../.team-work/betfair-exchange-20261010/final.txt) 嘅章節號，唔係呢幾份 docs 自己嘅章節號。要倚賴之前請睇返原頁。
- **仲係兩句、等 JSON 擁有者收窄嘅 value：** F03、F10、F37、F63。第二句應該搬去 code handling 或者 "Conflicts and open questions"；`test_betfair_facts_doc` 會對呢張清單同 JSON，而且唔准再多。
- **evidence_type · status**：證據類型，有第二個較弱來源就加 `secondary`；`·` 後面係 verification status。
- **retrieval**：點攞到。`official_rest_api_storage_read` 係經 Confluence REST API 讀全文；`zendesk_api_read` 係經 Zendesk API 讀 support article；`wayback_snapshot_<ts>` 係 live 頁返 HTTP 403，改讀存檔。一條事實嘅幾部分用唔同方法攞到嘅時候，JSON 嘅 retrieval 係一個 list，按 value 入面嘅次序（表入面用 ` + ` 連住）；引用 `local:` 來源嘅事實一定列 `local_python_check`。`live-test:` 來源冇 retrieval label（spec §15 冇呢個詞）。
- **source**：`DD/<id>` = `https://betfair-developer-docs.atlassian.net/wiki/spaces/1smk3cen4v3lu3yomq5qye0ni/pages/<id>`；`SA/<id>` = `https://support.developer.betfair.com/hc/en-us/articles/<id>`。舊 `docs.developer.betfair.com` 網址而家全部 301 去 atlassian。`forum <n>` = forum.developer.betfair.com 嘅 thread；`Python …` = docs.python.org/3.14 嘅頁。`live-test:T<n>:sha256:<receipt_sha256>` = 我哋自己 first-live-test 嘅私人收據（唔入 Git）；`receipt_sha256` 係收據目錄入面 `SHA256SUMS` 檔嘅 sha256，同一對 test id 同 sha256 一定要喺 `reports/betfair-live-tests-<YYYY-MM-DD>.json` 嘅 `first_live_tests_run` 出現。
- **published_or_updated**：頁面自己寫嘅日期；冇寫就係 `not stated`。**accessed** 係讀來源頁嗰日：2026-10-10；2026-10-12 第二輪重讀、有改動嘅 14 行（F18、F25、F30、F36、F39、F50、F51、F52、F57、F60、F61、F65、F69、F73）係 2026-10-12。live-test 收據嘅日期記喺 live-test report，唔改 accessed。
- **code handling**：代碼點樣處理，包括唔確定時揀咗邊個較保守嘅做法。

## Evidence labels

Betfair 係 exchange operator，所以 Betfair 自己嘅頁面算 `official_*`；Apple 嘅 man page 係 macOS 工具嘅官方文件，Python 自己嘅 docs 係 Python 標準庫嘅官方文件，所以都算 `official_*`（F68、F73、F74；F69）。F73 只係「之後係咪每次讀都彈 dialog」嗰半未驗證。F74 嘅 SQLite 部分同 F69 嘅 Python 3.14.6 檢查係本地檢查，結構欄位都標咗：`secondary` `inferred`，retrieval 加 `local_python_check`。`vendor_*` 只指 Bet Angel。`first_person_observation` 留畀我哋自己 first-live-test（T0–T10；T11 跟 live replace 一齊剔走）嘅收據：2026-10-13 嘅 delayed-key 收據之後，F01、F02、F03、F50、F51、F65、F66 有 `secondary` `first_person_observation`；收據只支持 value 嘅一部分，所以 status 冇變。冇人獨立重做過任何結果，所以呢度冇任何事實標成「已獨立核實」。

## Conflicts and open questions

以下每條嘅 status 都係 `conflicting`、`unverified`、`unknown`、`inferred` 或 `partially_unverified`。代碼揀較保守嘅做法，已知例外係 F39 正好 0.80／1.25 嘅邊界（見下）；first-live-test 只係觀察，唔會自動放寬任何規則。

- **F08** keepAlive／logout 用 POST 定 GET：頁面寫 POST，佢個 curl sample 就用 GET。代碼用 `session.sso_http_method`（預設 POST）；T2 兩樣都試。T1（收據 ca943553…）嘅 keepAlive 同 logout 都係 SUCCESS，但收據冇記用咗邊個 method，T1 亦唔解決 F08；T2 延後。

- **F18** order／match projection 嘅 listMarketBook、listCurrentOrders 同 listMarketProfitAndLoss 共用每個 account 3 個 concurrency（「共用」淨係 SA 講）；listClearedOrders 計唔計入，同埋計嘅係排緊隊定執行緊，DD 同 SA 講法唔同。代碼 in-flight 上限 2；listClearedOrders 而家另有自己嘅上限 2（[接入指南 §8](betfair-integration.md#8-read-path)），按 DD 較保守嘅讀法應該計埋入同一個 pool。

## First-live-test checklist

**每一項都要 Yu 明確同意、而且本人喺終端機前面先做。** 呢份 checklist 唔授權任何 live call。

- **結果放邊：** raw response 只放 `STATE_ROOT/profiles/<p>/live-tests/`（唔入 Git）。入 Git 嘅 report 只可以有 test id、status 同 error code、field 名、boolean、數量、時間長度、冇 id 嘅 CLI 命令，同私人收據嘅 sha256；只記日期（`run_date`），唔記幾點幾分。
- **先記收據：** 每個做完嘅 test 寫入一份新嘅 dated report `reports/betfair-live-tests-<YYYY-MM-DD>.json`，`first_live_tests_run` 每項係 `{"test_id": "T<n>", "receipt_sha256": "<私人收據 sha256>"}`。`receipt_sha256` 係私人收據目錄入面 `SHA256SUMS` 檔嘅 sha256。T8a 記做 `T8`；同一份收據要唔要再列做第二個 test id（例如 T8a 入面 T5 嘅 delayed 半）未有決定，今次冇列。其他觀察放喺同一份 report 嘅 `live_test_observations`。[Setup report](../reports/betfair-setup-2026-10-10.json) 唔改：佢嘅 status 講明冇 network call，所以佢嘅 `first_live_tests_run` 永遠係空。
- **再改標籤：** 有收據之後，下表「解決邊條」列出嘅事實先可以標 `first_person_observation`；`sources` 要加 `live-test:T<n>:sha256:<同一個 receipt_sha256>`，再更新 JSON 同上面對應嗰行。冇對應收據、或者 test 冇列呢條事實，`test_betfair_facts_doc` 都會拒絕呢個標籤。只有收據直接支持嘅事實先改；收據淨係支持 value 嘅一部分，就標 `secondary`，status 唔變；收據冇答到（例如 T4 `no_envelope_observed`、T8a 對 F60）就唔改，而且要喺 report 嘅 `facts_not_relabelled` 列明：`test_betfair_facts_doc` 會拒絕引用嗰份 report 收據嘅呢個標籤，亦要求 report 嘅 `facts_relabelled_secondary_first_person_observation` 啱啱好係 register 入面引用佢收據嘅事實。
